# FACAI：产品愿景与后续完善说明

**整理日期：** 2026-10-02  
**用途：** 让接手的产品/工程团队准确理解目标效果，并按可验收的步骤补齐项目。  
**依据：** 用户在本对话中反复确认的产品目标、当前源码 README、架构/部署/渠道文档及本日进度记录。  

> 本文把“设想目标”和“当前实现”分开写。目标描述不是已完成能力的声明。当前进度与证据请同时阅读《FACAI项目进度与交接_2026-10-02.md》。

## 一、FACAI 最初设想的产品是什么

FACAI 的核心不是一个只能聊天的机器人，也不是把若干 API 名称摆在页面上。它要成为一个用户能看见、能控制、能追溯的 AI 多任务工作台：用户用自然语言提出工作，FACAI 把要求整理成明确任务，调度适合的 Agent/模型并行执行，再把真实过程和结果放回一个可视化工作流中。

### 1. 用户从一句大白话开始

用户可从 FACAI 网页对话窗口，或已连接的消息渠道发来普通表达，例如“检查授权失败并修好”。FACAI 保存用户原话，不擅自改写覆盖；接着生成一份可读、可编辑的专业任务描述，标明目标、范围、约束、预期交付物和验收方式。

用户应能同时看到：

- 收到的原始消息；
- 转换后的专业任务/提示词；
- 系统准备采取的步骤与派发对象；
- 原话如何映射到任务要求的摘要或转换依据；
- 若信息不足、风险较高或需要外部授权，具体卡在哪一项。

目标是让用户明白“系统理解了什么、接下来要做什么”，而不是只看到一个不透明的“AI 正在思考”。

### 2. 自动拆成可视化、多线程工作流

FACAI 将一个较大的 Mission 分解为有依赖关系的步骤/子任务，形成可检查的 DAG 工作流。规划器可把相互独立的工作同时派发，例如：

| 分支 | 示例工作 | 交付证据 |
| --- | --- | --- |
| 功能实现 | 修复消息入口或新增任务分发能力 | 代码差异、提交/检查点、单项测试 |
| UI 与可用性 | 检查用户流程、修正网页布局 | 页面变化、浏览器验收记录 |
| 集成与兼容 | 验证模型、渠道、n8n webhook 等适配 | 成功/失败响应、配置状态、错误分类 |
| 独立审查 | 检查安全、回归、任务冲突 | 审查发现、复现方法、通过/不通过结论 |

相互依赖的工作按顺序运行；并行的代码任务必须在隔离的分支、worktree 或沙箱内工作。完成后由集成关卡执行代码审阅、冲突处理和测试，再汇总给用户。不能让多个写入者同时改同一工作目录，也不能把“API key 已配置”显示成“模型正在工作”。

### 3. 每个环节都能看见真实状态和进度

页面以 Mission 为中心，让用户从一屏找到任务进度、当前环节、子任务和结果。每个阶段/子任务都展示：

- 负责人 Agent、供应商、模型、执行 Runtime；
- 排队、运行、等待授权、等待依赖、失败、取消、完成等状态；
- 整数百分比，按 1% 为最小显示单位；
- 最近事件、开始时间、已用时间、重试次数与阻塞原因；
- 输入/输出摘要、日志、结果文件/代码差异、测试情况；
- 真实 token、上游费用及按产品规则计算的用户费用。

百分比必须来自可观测事件、明确里程碑或估算并标出估算性质。等待、无进展、调用失败时要如实显示，不得用循环动画或定时递增制造“正在工作”的假象。断线再打开后，页面应从数据库事件恢复同一状态。

### 4. 用户能从一个工作台管理任务，而不是被迫使用多个后台

FACAI 网页端是用户端的入口：新建任务、检查提示词、查看工作流、暂停/恢复/取消、重试、阅读交付物和费用都在这里完成。管理员另有渠道配置、模型/Agent/Skill/Runtime 注册、服务健康和租户管理能力。

n8n 可以作为内部自动化或事件编排的可选组件，但它不是产品目标本身。用户明确要的是 FACAI 具备任务分配和多 Agent 流程能力。优先补强 FACAI 原生队列/DAG；除非许可及架构已经确认，不应把 n8n 编辑器直接包装给付费用户，也不应把“n8n 容器启动”宣传为 FACAI 多 Agent 功能已完成。

### 5. 消息渠道与网页工作流共用同一条管线

接入微信、Telegram、WhatsApp 等渠道后，渠道消息与网页输入都进入相同的入口处理：验证收到消息 → 去重 → 保存原文 → 转成专业任务 → 创建 Mission/步骤 → 派发 → 记录执行 → 将结果关联回原渠道并展示在网页。

渠道状态必须分清代码已实现、凭据已配置、账号已授权、真实收发已验收。以个人微信为例，二维码能显示只是流程的一部分；必须由用户实际扫码，并验证收信、去重、派发、结果关联和重启恢复，才能标为线上通过。

### 6. 面向最多五名外部用户的隔离式付费服务

预期网页将来可向熟人/小范围用户收费，最多五人同时使用。每个人有各自的账号、历史记录、任务、消息记忆、模型/渠道凭据、成本/用量和产出；用户之间互不可见。平台管理员拥有明确且可审计的管理权限。

用户希望按经核实的 GLM-5.3 市价的 5 倍作为对客计价参考。真正收费前必须确认上游价格、币种、计价单位、缓存/工具/图片等不同费用，建立版本化费率、成本和售价分账、额度上限及超额阻断；价格没有依据时，不得生成看似精确的账单。

## 二、当前做到哪里了

当前代码已经有可运行的 Mission 工作台、队列、步骤事件、模型网关、认证、部分租户隔离、渠道适配器、n8n webhook 适配以及部署脚本；本地测试为 488 项通过。但这还不足以证明“多任务真正隔离并行”“最多五个付费用户安全可用”“各渠道生产可用”或“按价收费已完成”。

详细百分比和证据见《FACAI项目进度与交接_2026-10-02.md》。粗略总完成度约 60%，是相对于完整商业产品目标的工程估算，不是可直接对外承诺的质量分数。

## 三、接下来需要完善什么

### P0：先打通核心价值——一个任务拆分、多 Agent 真并行、可安全汇合

**现状：** 有持久队列、有限并发 worker、步骤依赖和状态事件；完整的单 Mission 多 Agent 并行开发闭环还不足。

**需要开发：**

1. 建立 Mission DAG 数据模型：节点、依赖、Agent、模型、Runtime、输入输出、重试策略和验收条件可持久化。
2. 做可配置规划/拆解层：生成 DAG 后先展示给用户/管理员检查，再按策略派发；保留大白话、专业提示词和结构化子任务之间的关联。
3. 给并行代码节点分配独立 worktree/沙箱、分支和文件权限；限制每个供应商、租户、任务的并发。
4. 实现汇合关卡：收集交付 → 检查差异 → 自动/人工处理冲突 → 运行相关测试 → 审阅通过后集成；失败时只重试失败节点，不丢失已完成证据。
5. 覆盖取消、超时、worker 崩溃、租约过期、重复派发、机器重启、上游 401/429/超额等恢复行为。

**验收：** 对同一个 Mission 创建至少三个节点，其中两个无依赖节点能真实同时运行在隔离目录；第三个等待前两者结果。网页能看到不同 Agent/模型的真实请求、输出、进度和费用。人为让一个节点失败/超时后，其他节点状态正确且可重试；集成阶段不得悄悄覆盖另一个节点文件。整个流程重启后仍能恢复并有完整事件记录。

### P0：让“进度条”有可信含义

**需要开发：** 定义每类任务的阶段/事件模型、百分比算法、是否估算的标识、阶段级总进度算法、无活动检测、阻塞说明和 SSE 断线恢复。关键节点变化必须和数据库事务/事件顺序一致。

**验收：** 每个阶段显示 0–100 的整数值，每次变化至少 1 个百分点；无新事件时不会自动上涨；后台队列空时显示“当前没有运行中的阶段”；任务卡住时显示最后事件和等待时长；刷新/断线重连后百分比与状态不跳变；页面所有状态均可通过服务端日志或数据库事件核对。

### P0：确认 API Worker 的真实工作能力

**需要开发：** 为计划支持的每个 Provider 明确协议适配器、模型标识、环境变量凭据引用、超时/重试、并发/预算限制、响应格式处理和错误分类。做连通性检查与小型真实任务验证；把每次请求的供应商、模型、任务 ID、HTTP 状态、耗时、token、费用、错误保存下来。密钥不得回传给网页或日志。

**验收：** 只有成功完成真实请求的 provider/model 才显示可用；已配置但未验证、余额耗尽、额度受限、认证失败、暂未派发都分别显示。两个不同 provider 执行同一 Mission 的并行子任务时，可从事件记录证实各自真的收到输入并返回结果。模型 key 本身不构成工作证据。

### P0：收费前完成租户隔离和权限审计

**需要开发：** 对所有读取/写入接口统一实施 tenant owner 检查，覆盖 Mission、步骤、jobs、消息、提示词、事件、成本、artifacts、checkpoint、下载、取消/重试、渠道绑定和配置。区分用户、租户管理员、平台管理员角色；模型/渠道凭据按租户隔离或明确限制为平台级。提供审计记录、数据导出和删除策略。

**验收：** 使用至少两个真实配置账号和自动化越权测试，覆盖直接 ID 替换、列表/搜索、SSE、附件下载、任务控制和并发竞态，任何跨租户请求都拒绝且无数据侧信道。完成五用户并发测试、会话过期/注销/限流验证和备份恢复演练。达到这些标准前只适合内部试用，不适合承诺付费客户隔离。

### P0：实现可信成本、定价与硬限额

**需要开发：** 取得 GLM-5.3 官方价格和单位，建立带生效日期和版本号的费率配置；分别处理输入/输出 token、缓存、搜索、图片/视频、工具调用及币种换算。保存供应商实际成本和用户售价明细，按 ×5 规则计算并可追溯。按用户设置余额/周期额度、告警、硬停止和管理员调整流水。

**验收：** 用官方价格样例和边界值测试舍入/换算；每个任务页面及用户账单都展示数量、单价、费率版本、成本和售价；达到预算后不会继续创建新的收费请求；未知或缺少用量信息时清楚标“无法计费/待核对”，不能猜费用。

### P1：完成真正的消息渠道授权和端到端测试

**需要开发：** 首先修好个人微信授权弹窗/二维码数据、过期刷新、扫码状态轮询和授权后收信；再验证消息去重、原文保留、任务转换/分发和回传。之后按 Telegram、WhatsApp 官方接入流程分别配置 webhook/凭据。逐步扩展媒体，不先宣称图片、语音、群聊等尚未支持的能力。

**验收：** 在专用测试帐号完成真实扫码授权、收一条、回一条和服务重启恢复；同一平台消息重复投递不得产生多个 Mission/收费任务；失败能显示平台错误。网页与渠道看到相同的任务 ID 和最终状态。

### P1：把关键用户操作完整走查一遍

**需要开发：** PC 和手机实机检查登录、创建任务、查看/编辑提示词、确认拆解、派发、并行状态、等待授权、失败恢复、结果/代码差异、费用、历史查询。修复截图中步骤卡片过窄导致文字逐字竖排的问题、长日志折叠/复制、错误提示和无任务时的入口引导。

**验收：** 以未参与开发的用户身份完成从登录到交付的任务；不查开发者工具也能判断“从哪里开工、谁在做、为什么等待、怎么查看结果”。PC/手机无横向溢出、无乱码，键盘与屏幕阅读基本可用。进度可视化必须与服务端事件一致。

### P1：发布、回滚和上线运营准备

**需要开发：** 确认生产当前提交与本地未提交差异；代码审查后形成干净可回滚版本；发布前备份数据库、配置和 workspace；部署后检查登录、HTTPS、SSE、Mission 创建、worker、真实模型、费用、队列重启恢复；准备告警、日志留存、数据保留和事故处理流程。

**验收：** 从网页真实操作确认版本变化；记录上线 commit、数据库备份、健康检查、端到端样例和回滚方法。未验证的外部服务显示未配置/未验收。

### P1：安全地导入与运行 Skills

**需要开发：** 记录来源、许可证、固定版本和哈希；解析 Skill 内容但先不执行；管理员审查/启用；按用户授权在隔离环境中运行，并对文件、网络、命令、时长和输出设定限制；完整记录版本与运行事件。

**验收：** 恶意/越权 Skill 的文件和网络访问按策略拒绝；删除/撤销后不能继续被任务引用；每次执行可追溯到用户、Mission、Skill 版本和权限范围。

### P2：决定数据和 n8n 的长期架构

当前服务器为 4 核、8 GB，SQLite、单机 worker 可以支持早期小规模验证，但五人同时做长任务前须测并发与锁等待。压测证明单机存储到达瓶颈后，再规划 PostgreSQL/Redis、后台 worker、对象存储和队列迁移。

n8n 当前是私有容器，尚未新建工作流，也没有连 FACAI 生产 webhook；这不是 FACAI 原生任务分发已完成的证据。优先测 FACAI 自身 DAG 是否满足需求。如果要在付费产品中托管客户工作流/凭据或暴露 n8n 编辑能力，先确认对应商业许可和产品边界，再决定是否把它作为后台依赖。

## 四、推荐实施顺序和阶段门

| 阶段 | 结果 | 完成后再进入下一阶段 |
| --- | --- | --- |
| A. 建立可信基线 | 审阅全部差异、备份生产、定义 DAG/事件/费用 schema、确认模型与费率 | 工作树和生产提交差异清楚、可回滚 |
| B. 多 Agent 核心闭环 | 同一 Mission 中真实并行节点、独立工作树、汇合/冲突/测试/恢复 | 三节点验收通过，重启/失败测试通过 |
| C. 真实进度与交互 | 实时事件 UI、1% 整数进度、阻塞状态、PC/手机走查 | 前端显示与服务端事件逐项对齐 |
| D. 安全与计费 | 多租户越权测试、凭据安全、价格版本、预算硬停止 | 两个租户隔离与账单样例通过 |
| E. 渠道/模型验收 | 实际 provider 请求及微信等渠道授权/收发 | 每个能力有成功证据，未通过项标注清楚 |
| F. 灰度和公开服务 | 备份、压测、监控、发布、回滚、五用户验收 | 管理员确认授权后才开放目标客户范围 |

并行开发可以用于彼此不冲突的模块（例如 DAG/worker、租户审计、UI 验收），但必须定义文件边界和集成负责人。不能把多个 API 同时调用本身当作进展；每份工作都要有代码差异、测试、运行证据和接受/拒绝记录。

## 五、给后续开发团队的产品验收总句

只有当一个普通用户能从网页或已授权渠道提交一句自然语言要求，看到未篡改的原话和可审查的专业任务，看到多个真实 Agent 在隔离环境按依赖并行工作、看到每阶段按 1% 刻度变化且能追溯到事件，最后拿到经过测试和审阅的结果及可信费用；同时五名用户的数据/凭据彼此隔离、超额被硬性拦截、服务可以备份恢复并安全回滚，FACAI 才达到“可收费对外使用”的目标。
