## 目标产品效果（交给接手者的验收定义）

1. 用户在 FACAI 对话/消息入口用自然大白话提交要求。系统逐字保存原话，并同时展示“转换后的专业任务说明”和转换依据；用户能看懂系统将做什么。
2. 系统把任务拆解成可审查的阶段/节点 DAG。每个节点显示依赖、负责人 Agent、模型/API、Runtime、状态、真实百分比、耗时、最近事件、输入/输出摘要、错误和重试记录。
3. 互相独立的节点可以并发派发给不同 Agent/API；共享依赖的节点按依赖顺序运行。并行代码任务各自在独立工作树/目录，完成后经测试和冲突检查再合并，不能多个 Agent 同时写一个目录。
4. 进度每次以 1% 整数刻度展示，但百分比由可观测工作量、节点状态或明确里程碑计算；等待/失败时要显示原因，不能让动画冒充工作。
5. 每个任务都能在一个可视化工作流里查看原话、转换提示、API 路由、真实执行日志、代码差异、测试、交付物、checkpoint 与费用。用户能够一眼分辨“排队、运行、等待用户授权、失败、完成”。
6. 多客户登录时，各自 Mission、消息记忆、提示词、执行记录、成本、API 配置和配额相互隔离；平台管理员拥有显式管理权限。任何用户不能读取或控制另一租户资源。
7. 按已审核的 GLM-5.3 上游价格表 × 5 计算展示费用；记录费率版本、计价单位、tokens/调用、币种、成本/售价和费用上限。超过额度应阻止新调用并说明原因。价格未知时不得显示虚构账单。
8. 渠道接入真实账号后，入口消息与网页端 Mission 共用同一分发管线；只有真正收到上游确认才显示已授权/已发送。

## 给接手 AI 的执行指令

1. 先阅读本文件、`facai-cloud/README.md`、`docs/ARCHITECTURE.md`、`docs/CLIENT_DELIVERY.md`、`docs/DEPLOYMENT.md` 与 `docs/CHANNELS.md`，再查看 Git status/diff；本地未提交变更都是交接输入，不能覆盖。
2. 先完成 P0 任务并逐步提交。优先实现“单 Mission 多 Agent DAG + 子任务工作树隔离 + 实时可审计进度”，随后完成多租户/费用门槛。
3. 任务确实需要模型 API 时，只用已在安全 provider 环境配置并成功验证的 API；建立单独任务运行记录，不能说 API key 存在就代表模型正在工作。GLM 若资源不足应如实切换。
4. 每完成一项先跑对应测试，再跑 `python -m pytest -q`；只有达到真实验收标准才把任务/阶段标成完成。模型建议必须由 Codex/开发者审查后合入。
5. 不要对外开放 Docker 端口 5678，不要把 n8n 云试用当成部署依赖，不要使用客户生产消息试功能，不要在没有明确价格来源时收款。
6. 部署必须先检查生产当前 HEAD 和备份，再部署这个已通过测试的准确提交；部署后现场验证网页真正出现改动，并更新 `docs/DEPLOYMENT_RECORD.md`。
